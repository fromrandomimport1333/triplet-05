# City Brain: timeline and logs (report paragraph)

**What.** The timeline is the screen the jury watches during the demo (R3) and the source of the per-scenario log files (R2). It shows, live and with millisecond timestamps, what happens across the three layers: a Twin reading crossing its alert threshold, Guardian's verdict on that sensor, the incident the Brain opens, the LLM and rule proposals, the decision with its score against the alternatives, the signed command, the Twin's acknowledgement and the confirmed effect. Refusals, rejected messages and alerts show in red, and safe mode in amber.

**How.** A small stdlib service subscribes to the Brain's external and internal topics and to the Twin and Guardian topics. It turns each message into one readable row, tagged with its layer. Raw readings (about 200 per second) are not listed. They feed the live city map (water and smoke per zone from the readings the Brain believes, traffic on the roads, device states, Guardian's verdict per sensor, units driving between zones, command beams and safety refusals) and its sparklines, and only a reading that crosses its alert threshold or serves as evidence for an incident becomes a row. Envelopes are opened and their HMAC is checked, so every external row carries a lock mark, or a broken lock when the signature is wrong. Rows of the same `correlation_id` share a coloured bar. Hovering a row highlights its whole cause-and-effect chain, and clicking it opens the chain with the graph's `/chain` view when that service answers. The page is a single HTML file with inline CSS and JavaScript, served by `http.server` with Server-Sent Events, so it works offline in any browser. A `brain/control/run` start message opens `logs/<scenario>-<date-time>.log`, and the stop message closes it. Every row, with the full body of each Brain event and error, is written as one JSON line and flushed at once.

**Why.** The jury must see cause and effect across three teams' systems in a few minutes, from several metres away. That is why the page shows one line per meaningful step, large fonts, one colour per layer and a visible link between the steps of a chain, rather than a raw message dump. The lock marks make the signature checks visible. Server-Sent Events need no library and reconnect on their own, picking up missed rows by sequence number, and no internet is needed at the venue. Flushing every line and naming the file after the run's own start time mean a crash loses nothing. A restart during a run continues the same file, so each run leaves exactly one log.

**Limits.** Rows are ordered by arrival and stamped with the producer's clock, so a layer whose clock drifts shows slightly out of order. The chain view relies on every team copying the `correlation_id`, and Twin acknowledgements are linked to their chain through the Brain's command id. When the graph API is down, a chain shows only the rows still in memory (the last 2,000). The screen has no login and listens on the local machine by default. It must not be exposed beyond the demo network.
